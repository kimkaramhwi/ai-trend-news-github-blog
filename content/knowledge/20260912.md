## 한 줄로 말하면

OpenAI는 ChatGPT를 포함한 자사 제품 전체의 데이터 접근을 담당하는 플랫폼 'Habitat(해비탯)'을 단순 라이브러리에서 초당 7천만 건 요청을 처리하는 분산 서비스로 키워냈다.

---

## 왜 중요해요

우리가 ChatGPT에 로그인하거나 새 대화를 시작할 때, 화면에 응답이 뜨기까지 내부에서는 수십 번의 데이터 조회가 일어난다. 이 조회가 느리면 서비스가 느껴지고, 실패하면 서비스가 아예 멈춘다.

OpenAI는 이 문제를 해결하기 위해 Habitat이라는 온라인 스토리지 플랫폼(online storage platform, 데이터를 빠르고 안정적으로 읽고 쓰는 중간 계층)을 직접 만들었다. 지금 Habitat은:

- **초당 7천만 건 이상**의 요청을 처리하고
- **매주 10억 명 이상**의 사용자를 지원하며
- **약 40개 지역**에 걸쳐 **500페타바이트(PB, 1PB = 100만 GB) 이상**의 데이터를 서빙한다.

단순히 규모가 크다는 게 아니라, **연간 10배 이상의 성장이 3년 연속** 이어지는 상황에서 이를 버텨냈다는 점이 핵심이다.

---

## 자세히

### 🌱 시작은 작은 Python 라이브러리였다

Habitat은 2024년 중반, ChatGPT 메인 서버에 연결된 작은 **Python 클라이언트 라이브러리(client library, 개발자가 코드에 가져다 쓰는 기능 묶음)**로 출발했다. 목표는 단순했다: 제품 개발자들이 데이터베이스 관리를 직접 신경 쓰지 않아도 되게 하자.

Habitat이 대신 처리한 것들:
- **스키마 조회(schema lookup)**: 어떤 형태의 데이터인지 파악
- **라우팅(routing)**: 데이터를 어디서 가져올지 결정
- **인가(authorization)**: 이 요청이 허용되는지 확인
- **암호화(encryption)**: 데이터 보안 처리
- **커넥션 풀링(connection pooling)**: 데이터베이스 연결을 효율적으로 재사용

백엔드 스토리지로는 **Azure Cosmos DB**(마이크로소프트의 클라우드 데이터베이스 서비스)를 사용했다. 이 라이브러리는 중앙의 강제 없이도 제품 개발자들 사이에 빠르게 퍼져나갔다.

---

### 🚧 라이브러리의 한계: 조율의 악몽

2025년 중반이 되자 Habitat은 라이브러리 방식의 한계에 부딪혔다. 대표적인 사례가 있다.

특정 중요 데이터를 단일 지역 장애 시 피해를 줄이기 위해 여러 지역에 분산된 Azure Cosmos DB 계정으로 이전하려 했다. 이를 위해 클라이언트에 추가 **라우팅 로직**을 심고, **피처 플래그(feature flag, 특정 기능을 켜고 끄는 스위치)**로 제어한 뒤, 수십 개 서비스 팀에 순차적으로 배포해야 했다.

그 결과:
- 배포 조율만 **수 일** 소요
- 로직 검증을 위한 **섀도잉(shadowing, 실제 트래픽을 복제해 새 로직으로 테스트하는 방식)** 도입에 또 **수 일**
- 버그 발견 후 수정 배포에 **또 수 일**
- 최종적으로 플래그를 활성화하려는 순간, 한 팀이 무관한 이유로 **이전 버그 버전으로 롤백**하면서 그토록 막으려던 장애가 발생

수십 개 서비스에 걸친 클라이언트 업데이트 조율은 **점점 더 취약하고 비효율적**이 되어갔다.

---

### 🏗️ 라이브러리 → 독립 서비스로의 전환

해결책은 Habitat을 **독립적인 서비스(standalone service)**로 분리하는 것이었다. 이로써 얻은 것:

- **배포의 단일 제어점**: 모든 제품이 즉시 개선 혜택을 누림
- **관찰 가능성(observability)**: 문제를 한 곳에서 추적 가능
- **강력한 데이터 보안**: 접근 제어 정책, 감사 로그, 외부·내부·에이전트 행위자로부터의 무단 접근 차단을 중앙에서 일괄 적용

---

### 🐍 Python으로 고성능 서비스를? 전략적 기술 부채

흥미로운 점은, OpenAI가 서비스 전환 시에도 **Python을 유지**했다는 것이다. Python은 고처리량(high-throughput) 서비스에서 네트워크 지연과 CPU·메모리 비용을 높이는 단점이 있다.

그럼에도 Python을 선택한 이유는 명확한 **전략적 판단**이었다. 원문에서 팀은 이를 "전략적 기술 부채의 의도적 수용"이라고 표현한다. 당장의 효율보다 빠른 배포와 안정성 확보가 우선이었고, 100배 규모에서는 결국 재작성이 필요할 것임을 인지하면서도 그 시점을 위한 시간을 버는 것이 목표였다.
